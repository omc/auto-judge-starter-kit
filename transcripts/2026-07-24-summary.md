## Key discussion notes

- **What we're building:** an LLM-as-judge, not a retrieval system. The task is to judge documents for relevance against a query/topic; retrieval is not the point.
- **Track structure (Nate/Max walkthrough):**
  - Track → _domains_ (rag, Ragtime, Dragon, Biogen, iCat — names partly unclear from transcript); each domain is a dataset.
  - Each domain has _topics_ = an information-need description + a query.
  - Each domain also ships _documents_ as jsonl/TSV dumps; historically you build your own index. Indexes are mostly plain text, not heavy numeric/structured (not e-commerce-grade multi-field) data.
- **Query vs. query+information-need:** historically IR systems could use just the query (short) or query + information need (closer to a system prompt). Max was drawn to inferring the information need from the query alone as the "real-world" scenario, but Nate noted judges normally _do_ receive the information need in context — so for the judge task we should use everything provided.
- **Submission mechanics (Nate's read, to be confirmed):** judge ~5,000 documents that the ~50 participating teams placed in their top 100, then compare our ratings against the coordinators' ratings via cross-ranker/inter-annotator similarity — Cohen's Kappa, Krippendorff's Alpha, Jaccard overlap. Referenced in the proposal.
- **Idea (Max):** run retrieval on the index with a tuned ranker and feed the document's rank/position into the judge prompt as a feature ("this doc appears after X, before Y — is it relevant?"). Nate: good prompt engineering.
- **Domain focus:** you can focus on specific domains and don't have to do every task. Historically ~4 strategies/submissions allowed (Nate unsure if that changes this year since it's auto-ranked). Max wants a _general_ solution (Bonsai serves varied customers); Nate flagged rag and Ragtime as the general-knowledge domains and a good next-meeting target; Biogen likely off-target for Bonsai.
- **Data format:** legacy TREC — TSVs, no headers, essentially unchanged since ~1992. Called out as the hardest part to deal with.
- **Repos:** the _starter kit_ is what we fork and build in; the _evaluate_ repo is TREC's own (computes the leaderboard) — theirs, not ours to fork.
- **eval vs. qrels:** qrels = gold data; eval = what our judge produced. Eval measures include relevance (float 0–1) and completeness.
- **Repo status:** Max forked the starter kit into the OMC private org, ran the Claude setup, downloaded the dataset, and ran the "kiddie" smoke test via a free OpenRouter endpoint. It ran, but the raw outputs are hard to interpret — wants a visualizer. Nate has built bespoke visualizers before (a Shiny app) but never maintained them. Fork was ~63 commits behind; Max walked through pulling from upstream (hit merge conflicts live).
- **Tooling/workflow:** Alli suggested a running "vlog"/notebook of what was tried and the outputs. Nate historically used numbered Jupyter notebooks. Max prefers Python scripts / per-judge directories (notebooks get run out of order). Consensus: use whatever's comfortable, keep both if useful, but the final deliverable must be executable Python — they won't accept notebooks.
- **Collaboration:** everything open (must be submitted at the end; no trade secrets). Keep papers, notes, and markdown in the repo rather than spreading across tools. Considering inviting Chris Max — doing her Master's in Perth, Australia — as a possible async contributor; Alli to reach out.

## Findings

- The deliverable is an LLM judge; success is measured by agreement with coordinator ratings (Cohen's Kappa / Krippendorff's Alpha / Jaccard), not retrieval quality.
- 2025 judgment data is likely already published, so the team can run **mock meta-evaluations against last year's data** to pick strategies before committing.
- Submissions are judged _before_ that year's judgments are released — deliberately, to prevent teams from poisoning/training judges on the answers.
- "Umbrella" is a ~2023 paper (out of Bing) likely used as the baseline — not a team.
- The kiddie smoke-test pipeline runs end-to-end locally on a free OpenRouter endpoint.

## Notes for the research paper

- **Prior art (Nate):** two previous TREC entries. The winning one (~2022) was a sparse + transformer (sentence-transformer) hybrid whose best run was token recall + vector rescore — evidence that a vector-DB first phase (vector recall) isn't necessary. Podcast/Spotify track used ~100,000 English-language transcripts.
- **Methodology hook:** feeding a document's retrieved rank/position (from a separately tuned ranker) into the judge prompt as a signal — a testable idea worth ablating.
- **Meta-evaluation plan:** validate candidate judge strategies against published 2025 judgments before submission; report agreement via Kappa / Krippendorff's Alpha / Jaccard.
- **Baseline:** "Umbrella" (~2023, Bing) as the reference/baseline judge to beat or compare against.
- **Positioning:** the team frames LLM-as-judge as a fresh frontier (vs. e.g. approximate-nearest-neighbor, which Max has deep paper-reading experience in), motivating a literature review of the 2025 participant papers as step one.
- **Open research angle:** using this framework for visual-language / image understanding (Nate's work-adjacent interest) — noted, not committed.
